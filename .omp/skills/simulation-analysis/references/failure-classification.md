# 失败分类启发式（failure classification）

> 供 `simulation-analyst` 在证据基础上判断问题归属，并标注置信度。
> 分类结论必须来自工具证据，不得仅凭日志末行错误下结论。

## 四类问题

| 类别 | 含义 | 典型线索 |
| --- | --- | --- |
| 环境（Environment） | 编译/仿真器/路径/库配置问题 | 仿真未启动、找不到文件/库、license 错误、命令行参数错 |
| 工具（Tool） | 仿真器/工具自身 bug 或版本差异 | 同一 RTL 在不同仿真器结果不一致、工具 crash、内部报错而非断言 |
| 验证（Verification） | testbench/激励/参考模型问题 | 预期值来自 TB 而非 DUT、激励覆盖不足、参考模型错误 |
| 设计（Design） | DUT 逻辑错误 | assertion 触发于 DUT 内部信号、数据比对失败指向 DUT 输出 |

## 判别线索（按优先级）

1. **仿真能否启动**：不能 → 环境/工具（看报错是路径/license 还是工具内部）
2. **失败位置**：在 DUT 内部信号/输出 → 偏设计；在 TB 预期值计算 → 偏验证
3. **跨仿真器一致性**：一致 → 偏设计/验证；不一致 → 偏工具
4. **首个失败时间点**：早期（初始化/复位）失败 → 偏环境/复位逻辑；功能场景失败 → 偏设计/验证
5. **警告是否相关**：Width mismatch 等警告若与失败信号相关 → 验证或设计；无关 → 可忽略

## 置信度标注

| 置信度 | 适用 | 写法示例 |
| --- | --- | --- |
| 高 | 证据直接指向单一类别（如仿真器报 license 失败 → 环境） | `环境 / high` |
| 中 | 证据指向但存他因（如功能失败但仍有未排除的 TB 缺陷） | `设计 / medium` |
| 低 | 证据不足，需进一步手段（波形/代码交叉） | `设计 / low（待 rtl-analyst 补充结构上下文）` |

## 协作

- 不确定是否设计问题时，调用 `rtl-analyst` 补充结构上下文（信号/模块/时钟域）
- 不确定是否测试环境问题时，调用 `verification-engineer` 判断
- 任何低置信度结论必须写入报告的「不确定性」段，不得伪装为确定根因

## 诚实边界

- 不把日志中最后一个错误误认为首要根因——以 `extract_failures.py --first-only` 的首个失败为准
- 波形/时序类证据当前工具未实现（Milestone 4），不得用其作为分类依据
